# レセコンシステム 詳細設計書

- 版数：0.1（ドラフト）
- 作成日：2026-07-09
- 上位文書：`docs/レセコン要件定義書.md`（要件ID）、`docs/レセコンWBS.md`（WBS 4.1〜4.9 に対応）
- 本書の位置づけ：基本設計（アーキテクチャ・データモデル・外部連携方針）を前提に、実装可能なレベルまで各コンポーネントの内部構造・データ定義・処理フローを規定する

> **注記**：オンライン資格確認等システム・電子処方箋管理サービス・電子カルテ情報共有サービスの電文レベル仕様は、医療機関等ONSサイト掲載の外部インターフェイス仕様書（8.09版以後等）に定義される。本書ではONS仕様に依存する箇所を「※ONS仕様準拠」と表記し、電文項目の転記は行わない（版更新への追随はアダプタ層で吸収する設計とする）。

## 2. テナント・認証認可設計（WBS 4.8）

### 2.1 認証

| 項目 | 設計 |
|---|---|
| 方式 | OIDC（Authorization Code + PKCE）。IDaaSまたは自前認証基盤 |
| 二要素認証 | 必須（NFR-15）。第2要素：TOTP または FIDO2/パスキー。医療機関ポリシーで選択 |
| パスワードポリシー | 最低12文字・複雑性要件、入力不成功時の遅延、連続失敗5回でアカウントロック（管理者解除またはクールダウン30分） |
| セッション | アクセストークン有効期限60分、リフレッシュ8時間（診療時間帯運用を考慮）。アイドルタイムアウト30分 |
| 端末制約 | テナント単位でIPアドレス制限（許可リスト）を設定可能 |

### 2.2 テナント分離（AR-12〜14, NFR-16）

| 項目 | 設計 |
|---|---|
| 分離方式 | 単一DBクラスタ内で**テナント別スキーマ分離**を基本とする。全業務テーブルはテナントスキーマ配下に配置し、共有スキーマ（common）にはテナント台帳・共通マスタのみ配置 |
| テナント解決 | JWTクレーム `tenant_id` → 接続時に `search_path` 固定。アプリ層でのクロステナントアクセスは接続レイヤで物理的に不能とする |
| ソースコード | 全テナント共通の単一コードベース（AR-13）。テナント差異は `tenant_settings`（機能フラグ・帳票レイアウト選択・運用パラメータ）で吸収し、コード分岐によるカスタマイズは行わない（AR-14） |
| オプション機能 | `feature_flags` テーブルでON/OFF。全テナントが選択可能な機能のみ登録可 |

### 2.3 認可（RBAC）

| ロール | 主な権限 |
|---|---|
| system_admin（ベンダー側） | テナント管理、マスタ配信、機能フラグ操作。**患者情報の参照権限なし**（権限分離、NFR-16①） |
| audit_admin（ベンダー側） | 監査ログの参照のみ。システム設定権限と分離 |
| tenant_admin（医療機関） | 自テナントのユーザー管理、設定、IP制限 |
| medical_clerk（医事課） | 患者・保険・会計・レセプト業務の全操作 |
| reception | 患者・保険情報の登録・照会、資格確認 |
| viewer | 参照のみ |

- 権限判定は「ロール×リソース×操作」のパーミッションマトリクスで実装。APIごとに必要パーミッションをアノテーション定義し、認可ミドルウェアで一元チェック
- ベンダー管理者権限は申請ベースの一時付与（Just-in-Time）とし、付与・行使を監査ログに記録

## 3. データベース詳細設計（主要テーブル）

命名規則：スネークケース。全テーブル共通カラム：`id (UUID, PK)`, `created_at`, `created_by`, `updated_at`, `updated_by`, `version (楽観ロック)`。論理削除は `deleted_at`（診療報酬関連レコードは物理削除禁止）。

| name_kanji | varchar(100) | NOT NULL | 姓名は半角スペース区切り |
| name_kana | varchar(100) | NOT NULL | |
| birth_date | date | NOT NULL | |

| postal_code / address / phone | | | |
| death_flag / death_date | | | |
| memo | text | | 医事メモ |

**insurances（保険資格）**

| カラム | 型 | 備考 |
|---|---|---|
| patient_id | UUID FK | |

### 3.3 算定・会計（billing-svc）

**calculations（算定結果）**：encounter_id、共通算定モジュール要求ID、算定結果（jsonb：点数明細）、総点数、モジュールバージョン、算定日時、状態（calculated/error/superseded）。再算定時は旧レコードを superseded とし履歴保持。

**payments（会計）**：encounter_id、請求額、患者負担額、公費按分、収納額、収納方法、未収フラグ、領収書番号（テナント内連番、年度リセット）。

### 3.4 レセプト（receipt-svc）

**receipts（レセプト）**

| カラム | 型 | 備考 |
|---|---|---|
| patient_id | UUID FK | |
| billing_month | char(6) | 診療年月 YYYYMM |
| insurer_type | varchar(2) | 提出先（支払基金/国保連合会） |
| status | varchar(12) | draft / checked / submitted / accepted / returned / resubmitted |
| total_points | integer | |
| record_data | 外部参照 | UKE形式レコード本体はオブジェクトストレージ格納、パスを保持 |
| submission_id | UUID FK | 提出バッチへの参照 |

**receipt_errors（チェック結果）**：receipt_id、チェック種別（形式/資格/算定/固有）、エラーコード、内容、解決状態。

**submissions（請求バッチ）**：請求年月、提出先、件数、合計点数、UKEファイルパス、提出日時、受付結果。

**returns（返戻管理）**：receipt_id、返戻理由コード、返戻年月、再請求先receipt_id。

### 3.5 共通基盤

**audit_logs（監査ログ）** ※8章参照。**users / roles / user_roles / permissions**。**tenant_settings / feature_flags**。**masters_***（点数表・医薬品・特定器材・保険者・住所等。version列で世代管理し改定日で切替）。

## 4. 機能詳細設計

### 4.1 患者・保険情報管理（FR-01、WBS 4.1）

**主要画面**：患者検索、患者登録・編集、保険情報編集、資格確認結果確認。

**処理フロー：患者登録**
1. 入力検証（カナ正規化、生年月日妥当性、診察券番号重複チェック）
2. 類似患者検索（カナ氏名＋生年月日＋性別）→ 候補があれば警告表示（二重登録防止）
3. 登録、監査ログ記録（対象患者ID・操作者）

**処理フロー：オンライン資格確認による保険情報更新**
1. 受付時、院内接続エージェント経由で資格確認端末に照会要求（※ONS仕様準拠）
2. integration-svc が応答を受領 → patient-svc へ資格情報を連携
3. 既存 insurances と差分比較 → 差分ありの場合は「資格変更あり」として画面に警告、確認操作後に新レコード追加（旧レコードは valid_to を設定して履歴保持）
4. verification_result / verified_at を更新

### 4.2 診療行為取込（FR-02、WBS 4.1）

- **電カル連携取込**：連携APIで受領した診療行為を `source_ref` で冪等に登録（同一refは更新扱い）。取込単位はencounter。マスタコード不在の場合はエラーキューに積み、画面で手動解決
- **手入力**：診療行為検索（名称・カナ・コード前方一致）、セット登録（よく使う組合せの定型セット。テナント単位で管理＝カスタマイズではなく設定データ）
- 診療行為確定時に encounter.status = closed とし、算定処理をトリガー

### 4.3 算定・会計（FR-03/04、WBS 4.2, 4.4）

**共通算定モジュール連携シーケンス**（詳細は5.1）

```
encounter確定 → billing-svc:算定要求組立（患者属性・保険・公費・診療行為明細）
  → integration-svc:共通算定モジュールAPI呼出
  → 応答（点数明細・加算・患者負担）を calculations に保存
  → payments 生成 → 会計画面へ反映 → 領収書・明細書発行
```

**患者負担金計算**：共通算定モジュールの算定結果を正とする。公費併用時の按分、負担上限管理（高額療養費・限度額認証の適用区分はオン資格取得値を使用）。端数処理は療担規則に基づく四捨五入。

**再算定**：診療行為の事後修正時、当日〜月内であれば再算定→差額を返金/追徴として payments に調整レコードを追加。

### 4.4 レセプト作成・請求・返戻（FR-05〜07、WBS 4.3）

**月次レセプト作成バッチ**
1. 対象抽出：billing_month の encounters（status=closed）を患者×保険単位に集約
2. レセプト生成：calculations を基にUKE形式レコード（電子レセプト作成手引き 令和6年9月版準拠）を生成。レコード種別（IR/RE/HO/KO/SI/IY/TO/CO…）ごとにビルダーを実装し、手引き改定時はビルダー差替えで対応
3. チェック：①形式チェック（レコード長・型・必須）②資格チェック（保険有効期間と診療日の整合）③算定チェック（共通算定モジュール結果との突合）④受付前点検（記録モレ・病名対応は将来拡張）
4. エラーは receipt_errors に記録し、点検画面で修正→再生成
5. 確定操作で status=checked → submissions にまとめてUKEファイル出力

**オンライン請求**：確定済みUKEファイルをオンライン請求システムへ送信（送信操作は医療機関の請求担当が実施。システムはファイル出力と送信記録管理を担う）。受付結果を submissions に反映。

**返戻・再請求**：返戻ファイル取込 → returns 登録 → 対象レセプトを複製して修正 → 再請求レセプトとして翌月 submissions に含める。原本は履歴として不変保持。

### 4.5 帳票・統計（FR-08、WBS 4.3）

| 帳票 | 内容 | 出力先 |
|---|---|---|
| 領収書・診療費明細書 | 会計確定時 | 院内プリンター（エージェント経由） |
| 日計表 | 日次収納集計 | PDF/CSV |
| 月報 | 診療科別・保険種別の点数/件数集計 | PDF/CSV |
| 請求管理表 | 請求・返戻・再請求の状況一覧 | 画面/CSV |
| 未収金一覧 | 未収レコード | 画面/CSV |

帳票生成はreport-svcで非同期実行（生成完了を画面通知）。PDFはオブジェクトストレージに保管し、署名付きURLで取得。

## 5. 外部連携詳細設計（WBS 4.4〜4.7）

### 5.1 共通算定モジュール連携（FR-11、WBS 4.4）

| 項目 | 設計 |
|---|---|
| 準拠仕様 | 診療報酬改定DXにおける共通算定モジュール外部インタフェース利用ガイド（製品版） |
| 呼出方式 | 同期API呼出（会計時のリアルタイム算定）。タイムアウト10秒 |
| 要求データ | 患者属性、保険・公費情報、診療行為明細（レセ電算コード）。組立は billing-svc、送信は integration-svc |
| 応答処理 | 算定点数明細・患者負担額を calculations に保存。応答の算定根拠（加算適用理由等）も保持し点検画面で参照可能とする |
| エラー処理 | 通信エラー：指数バックオフで3回リトライ→失敗時は「算定保留」状態とし会計を保留。業務エラー（コード不正等）：エラー内容を画面表示し診療行為修正を促す |
| バージョン追随 | モジュール改定の事前通知を受けて検証環境で回帰テスト（算定結果スナップショット比較）実施後に本番切替 |
| 冪等性 | 要求ごとに request_id（UUID）を付与。同一encounterの再算定は新calculationとして履歴管理 |

### 5.2 オンライン資格確認連携（FR-12、WBS 4.5）

| 項目 | 設計 |
|---|---|
| 準拠仕様 | ※ONS仕様準拠（外部インターフェイス仕様書 8.09版以後／WebAPI連携編 8.10版以後） |
| 構成 | 院内の資格確認端末⇔院内接続エージェント⇔integration-svc の3層。エージェントは端末の連携ファイル/APIを中継 |
| 主要ユースケース | ①受付時の資格確認（マイナ保険証/従来保険証）②一括照会（予約患者の前日照会）③薬剤情報・特定健診情報の取得同意処理（実装範囲は導入医療機関の運用に応じ設定） |
| データ反映 | 4.1「資格確認による保険情報更新」フローに接続 |
| 障害時 | 資格確認不可時は「未確認」フラグ付きで受付継続可能とし、事後照会キューに登録 |

### 5.3 電子処方箋管理サービス連携（FR-13、WBS 4.6）

## 6. 内部API設計

### 6.1 共通仕様

| 項目 | 設計 |
|---|---|
| スタイル | REST。パス：`/api/v1/{resource}`。バージョニングはURLパス方式 |
| 形式 | JSON（UTF-8）。日時はISO 8601（タイムゾーン付き） |
| 認証 | `Authorization: Bearer {JWT}`。全APIで tenant_id をJWTから解決（パラメータでのテナント指定は不可） |
| 追跡 | `X-Request-ID` 必須。レスポンスにエコーバック。監査ログと紐付け |
| エラー | HTTPステータス＋ `{code, message, details[]}`。将来のFHIR連携共通仕様（OperationOutcome）へ移行可能な構造にマッピング表を維持 |
| ページング | `_count`（上限100）＋カーソル方式。`next` リンクをレスポンスに含める |
| 排他 | 更新系は `If-Match: {version}` による楽観ロック。不一致は409 |

## 7. バッチ・非同期処理設計

| ジョブ | 起動 | 処理 | リカバリ |
